# ShopNova — Project Architecture

## Folder Structure

```
app/              # Next.js App Router pages and API routes
  (auth)/         # Clerk sign-in / sign-up routes
  (dashboard)/    # Admin dashboard route group (own sidebar/topbar layout)
  (marketing)/    # Storefront route group (storefront, cart, checkout, account)
  api/            # API routes (webhooks, AI endpoints)
components/       # Shared React components
  ui/             # shadcn/ui Base UI primitives (button, input, dialog, etc.)
  layout/         # Layout components (topbar, sidebar, container, ask-shopnova)
  storefront/     # Storefront-specific components (product-card, search-box, etc.)
  dashboard/      # Dashboard-specific components (active-carts-feed, etc.)
features/         # Feature-specific modules (cart, checkout, payment, shipping, etc.)
  admin/          # Admin logic + AI order triage
  cart/           # Cart store, session, context, actions
  checkout/       # Checkout logic + actions
  payment/        # Payment providers (Stripe, PayFast, Yoco, Stitch, Test)
  shipping/       # Shipping provider abstraction + couriers (Bob Go)
  account/        # Customer account logic
  search/         # Storefront search logic
lib/              # Utility functions, clients, validations
  auth/           # Admin authorization helpers
  db/             # Database helpers and Prisma client (orders, products, federation, etc.)
  federation/     # Mock federation source connectors
  validations/    # Zod validation schemas
hooks/            # Custom React hooks
types/            # TypeScript type definitions
prisma/           # Prisma schema, migrations, and seed scripts
  migrations/     # Database migrations
public/           # Static assets
scripts/          # Utility scripts (set-admin, test loader)
```

## Key Decisions

- **No `src/` directory.** All code at root for simplicity.
- **Next.js App Router** for routing and server components.
- **React + TypeScript** throughout.
- **shadcn/ui Base UI** for component primitives. Custom components built on top.
- **Prisma 7** for type-safe database access. Schema in `prisma/schema.prisma`.
- **PostgreSQL** as the database. (pgvector is not used by the MVP; it is a post-MVP roadmap item.)
- **Clerk** for authentication.
- **React Hook Form + Zod** for form validation. No Formik.
- **TanStack Query** is installed but not currently used in the application.
- **MVP scope.** Build only what's needed for a working product.

## Cart Architecture (Sprint 3, Part 1)

- **Storage:** Server-side cart behind a provider-agnostic `CartStore` interface (`features/cart/cart-store.ts`). Two backends implement it:
  - `RedisCartStore` (`features/cart/redis-cart-store.ts`) — production store backed by Upstash Redis (REST API), the guidebook's chosen cache. Used when `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are both set. Carts are stored under `cart:<shopper-id>` with a 30-day TTL (`60 * 60 * 24 * 30`) refreshed on every write via an atomic `SET ... EX` call.
  - `MemoryCartStore` — development-only fallback (in-memory `Map` on `globalThis`) that survives page navigation while the dev server runs. NOT production-ready (no cross-instance sharing, no restart survival).
- **Store selection:** `selectCartStore` (pure, unit-tested) chooses the backend: Redis when configured → `RedisCartStore`; no credentials + development → `MemoryCartStore`; no credentials + production → throws `CartConfigurationError` (production never silently falls back to an in-memory cart). The active store is resolved lazily on first use (not at module load) so `next build` does not require Redis credentials to be present at build time. Only the `CartStore` interface is imported by cart business logic, actions, checkout, and payments — swapping the backend never touches them.
- **Serialization:** Only the cart data needed by the cart architecture is stored (no full Prisma Product records). Money (`unitPrice`, `lineTotal`) is stored as the existing JS number snapshot captured at add-to-cart time; checkout re-reads authoritative prices from PostgreSQL, so the persisted snapshot is display-only. `serializeCart`/`deserializeCart` round-trip safely and reject corrupt/foreign payloads (degrading to an empty cart instead of crashing).
- **Concurrency:** Cart mutations follow a load → mutate → save cycle. The Redis `SET ... EX` write is atomic, but the read-modify-write window is not; two simultaneous mutations for the same shopper could race (last write wins). This matches the previous in-memory behavior and is acceptable for a single-shopper cart; distributed locking is intentionally not added (documented limitation).
- **Error handling:** If Redis is unavailable during an operation, `RedisCartStore` throws a `CartStoreError` with a generic, credential-free message; the original driver error is preserved on `cause` for server-side debugging. It never silently pretends the operation succeeded.
- **Shopper identity:** `features/cart/session.ts` resolves a shopper id per request — `user:<clerkUserId>` for signed-in shoppers, or `anon:<uuid>` stored in an httpOnly cookie for anonymous shoppers. No Customer database records are created by cart activity; customers are only created during checkout.
- **Price rule:** The client is never authoritative for price. Cart lines store a display snapshot (`unitPrice`) captured from PostgreSQL at add-to-cart time. Checkout re-reads authoritative prices from the database before creating an order.
- **Inventory:** The cart checks the `Inventory` model to prevent obviously invalid quantities (capping at available stock). Authoritative inventory validation happens during checkout; adding to cart does not reserve inventory.
- **Server actions:** All cart mutations run through server actions in `features/cart/actions.ts` (`addToCartAction`, `updateCartItemQuantityAction`, `removeCartItemAction`, `clearCartAction`, `getCartAction`).
- **Client bridge:** `CartProvider`/`useCart` (`features/cart/cart-context.tsx`) keeps the header badge and cart page in sync without turning the marketing layout into a client component.
- **Archived products:** `getCartAction` re-checks every cart line against the current product archive status. An archived line is shown as unavailable, excluded from the subtotal and header item count, and rejected at checkout (see Final MVP Audit below).
- **Tests:** Pure cart logic + the Redis cart store/selection are unit tested with Node's native test runner (`node --test --experimental-strip-types`). The Redis tests use a fake `RedisLike` client so `npm test` never requires real Redis credentials. Run with `npm test`.

## Checkout & Order Architecture (Sprint 3, Part 2)

- **Routes:** `/checkout` (requires a non-empty cart) and `/checkout/success?orderNumber=...` (confirmation).
- **Validation:** `lib/validations/checkout.ts` defines the Zod schema used by React Hook Form on the client and re-validated on the server before any checkout work. Clerk users get contact info prefilled (`useUser`); anonymous shoppers can complete checkout without signing in.
- **Authoritative pricing:** `features/checkout/actions.ts` `getCheckoutSummaryAction` re-reads product prices/inventory from PostgreSQL so the displayed order summary matches exactly what will be charged.
- **Order creation:** Order creation now happens ONLY after a server-verified payment notification, atomically inside `lib/db/payments.ts` `completePaidIntent` (see Payment Architecture below). The previous `createOrder`/`placeOrderAction` path was removed.
- **Order number:** `generateOrderNumber` in `features/checkout/checkout-logic.ts` produces a customer-facing `SN-YYYYMMDD-XXXXXX` number — the database `id` (uuid) is never exposed.
- **VAT & shipping:** Pure functions in `features/checkout/checkout-logic.ts` — 15% South African VAT and a deterministic MVP shipping rule (free ≥ $50, flat $5 below). Shipping is separated from the UI behind a `ShippingProvider` seam so a courier API can replace it later.
- **Tests:** 17 checkout unit tests in `features/checkout/checkout-logic.test.ts` (VAT, shipping, subtotal, total, quantity validation, insufficient inventory, order number format/uniqueness).

## Shipping Provider Architecture (Post-MVP #2)

- **Provider abstraction:** `features/shipping/shipping-provider.ts` defines the `ShippingProvider` interface (`id`, `isConfigured()`, `quote(request)`), `ShippingQuoteRequest` (origin, destination, parcels, subtotal, currency), `ShippingQuote` (provider, method, rate, currency, estimateDays), `ShippingAddress`/`Parcel`, `ShippingProviderError`, and the `ShippingProviderId` union (`mvp` | `bobgo` | `aramex` | `pudo` | `courier-guy`). Checkout business logic depends on the abstraction, never on a concrete courier. Provider-specific API details live inside adapters.
- **Pure logic:** `features/shipping/shipping-logic.ts` — destination completeness (type guard), address normalization, parcel/request building, `normalizeQuote` (defensive validation/coercion of provider responses), `selectCheapestQuote` (cents math, deterministic tie-break by provider id), and quote↔snapshot round-trip helpers. Dependency-free and unit-tested.
- **Registry:** `features/shipping/provider-registry.ts` (server-only) — `selectProvidersFromFactories`, `getConfiguredShippingProviders`, `collectQuotesFromProviders` (the guidebook's `Promise.allSettled` fan-out), `getShippingQuotes`, `getAuthoritativeShippingQuote` (cheapest valid quote), `getShippingOrigin` (env-configurable SA default), and `ShippingQuoteError`.
- **Provider strategy (per GUIDEBOOK.md):** when one or more live couriers are configured, ONLY those live couriers are queried — the deterministic MVP provider is intentionally NOT used as a silent fallback (a failed live quote must never be replaced with an arbitrary unverified price). When NO live courier is configured, the deterministic `MvpShippingProvider` is used (the documented deliberate fallback that preserves the existing MVP shipping behavior exactly).
- **Live courier status:** **Bob Go** (the guidebook's multi-courier API) is implemented and registered (`features/shipping/couriers/bobgo.ts`, Post-MVP #4) — it is selected only when `BOBGO_API_KEY` is present. Aramex, PUDO, and The Courier Guy adapters remain pending official API contracts/credentials. The deterministic `MvpShippingProvider` stays the documented fallback when NO live courier is configured.
- **Bob Go adapter (Post-MVP #4):** `BobGoProvider` implements `ShippingProvider` against the official public API contract (api-docs.bob.co.za): Bearer-token auth, `POST /rates` with a JSON body (`collection_address`, `delivery_address`, `parcels` with cm dimensions + kg weight, `declared_value`, `timeout`), sandbox (`https://api.sandbox.bobgo.co.za/v2`) selected by `BOBGO_TEST_MODE=true` and production (`https://api.bobgo.co.za/v2`) otherwise. It parses every documented response shape (a bare JSON array, `{rates|data|results}`, and `{provider_rate_requests[].responses[]}` with `status === "success"` filtering) and maps each rate to a `ShippingQuote` (`provider: "bobgo"`, `estimateDays: null` — the rates endpoint does not reliably expose delivery days, so none are invented). All credentials are server-side (`import "server-only"`); raw responses are validated by the existing `normalizeQuote` before influencing a total; driver errors are wrapped in `ShippingProviderError` (generic, credential-free message; original error on `cause`). Implemented per the official public API contract, unit-tested with mocked `fetch`, and **live-sandbox-verified** (Post-MVP #4 live verification): a real non-destructive `POST /rates` against `https://api.sandbox.bobgo.co.za/v2` with a Cape Town → Johannesburg test destination and a default 1 kg / 30×20×10 cm parcel returned real ZAR rates that normalized correctly into `ShippingQuote` and flowed through the registry + checkout path (destination gate, `selectCheapestQuote`, snapshot round-trip). No API discrepancy was found; no application code was changed for the live test. NOT marked production-verified (the production base URL has not been exercised, and per-product weight/dimensions remain a documented approximation).
- **Per-product weight/dimensions (Post-MVP #5):** the product schema now carries nullable per-product `weightGrams` and `lengthCm`/`widthCm`/`heightCm` (admin-editable). The shipping abstraction builds one parcel per purchased unit carrying the product's actual weight/dimensions when present (`parcelsFromLines` in `shipping-logic.ts`), so a Bob Go live quote now reflects the real goods. Products without physical metadata continue to receive the documented conservative fallback (`DEFAULT_PARCEL_WEIGHT_GRAMS = 1000` → 1 kg, applied by `parcelsFromLines`; `DEFAULT_PARCEL_*_CM` = 30×20×10 cm, applied per-field by `bobGoParcels` when a parcel omits a dimension — Bob Go requires dimensions ≥ 1 cm). The fallback is deterministic and applied per-field; zero values are treated as "not specified" (fallback); negative/non-integer values are rejected by the product validation schema. No weights or dimensions are invented silently.
- **Failure behavior:** if every configured provider fails or returns no valid quote, a `ShippingQuoteError` is thrown — checkout surfaces a safe user-facing error and creates no order with an incorrect amount. Provider driver errors are preserved on `causes` for server-side diagnostics and never exposed to the client. Forged/malformed provider responses are discarded by `normalizeQuote` before they can influence a financial calculation.
- **Quote flow (server-authoritative):** the client is never authoritative for the shipping rate, provider, quote, or order total. `createCheckoutIntent` obtains the authoritative quote from the validated destination through the abstraction, snapshots it on the `CheckoutIntent` (`shipping` amount + `shippingQuote` JSON), and computes the authoritative total. `completePaidIntent` reuses the snapshotted shipping (never re-fetches a live quote at order creation) so the order reproduces exactly what was charged. `getCheckoutSummaryAction` uses the abstraction when a complete destination is supplied (deterministic MVP estimate before the address is filled); `getShippingQuoteAction` exposes the abstraction for quote retrieval. The checkout view re-fetches the summary with the destination once the address is complete (RHF `useWatch`).
- **Client manipulation prevention:** the checkout form (`lib/validations/checkout.ts`) has no shipping-amount field; Zod strips any client-supplied `shipping`/`shippingTotal`/`shippingRate` keys. The order total is computed from the server subtotal + server quote rate + server VAT, never from a client value.
- **Order snapshot:** `Order.shipping` (amount) + `Order.shippingProvider` + `Order.shippingMethod` are captured at order time. Historical orders are never retroactively changed when shipping-provider rates change. The new columns are nullable, so existing orders (which used the deterministic rule) remain intact and display the amount only.
- **Schema change (additive, no data reset):** `CheckoutIntent.shipping` (Decimal, snapshotted amount) + `CheckoutIntent.shippingQuote` (Json, full quote snapshot); `Order.shippingProvider` (VarChar 40) + `Order.shippingMethod` (VarChar 100). All nullable/defaulted; no existing order or intent is modified.
- **Address validation:** reuses the existing checkout address fields (street, city, province, postal code, country). No checkout form redesign. Provider-specific address requirements are handled by mapping the application's address into the common internal `ShippingAddress` and doing provider-specific mapping inside each adapter.
- **Environment variables:** `SHIPPING_ORIGIN_*` (optional, SA defaults) configure the dispatch origin. `BOBGO_API_KEY` (Bearer token) + `BOBGO_TEST_MODE` (sandbox toggle) configure the Bob Go live courier; remaining courier credential variables are documented in `.env.example` as pending placeholders. Courier secrets are server-only and never reach the client.
- **Tests:** 55 shipping abstraction tests (`features/shipping/shipping-logic.test.ts` + `features/shipping/shipping-provider.test.ts`) + Bob Go adapter tests (`features/shipping/couriers/bobgo.test.ts`) cover the provider contract, quote normalization, provider selection, successful quote, provider failure, invalid/malformed responses, missing configuration, currency mismatch, shipping-cost calculation, checkout total integration, protection against client-supplied shipping manipulation, and the Bob Go request/response contract (every documented response shape, auth/config failures, HTTP/network errors, malformed responses, invalid rates, currency mismatch, registry integration, per-product weight/dimensions, quantity → one-parcel-per-unit behaviour, per-field fallback for missing dimensions, zero-as-missing). Uses `FakeShippingProvider` + the extracted pure registry helpers + mocked `fetch`; no real courier credentials required. Total suite: 341 tests (including product physical-field validation tests). The Bob Go adapter is additionally **live-sandbox-verified** — a real `POST /rates` to the Bob Go sandbox returned real ZAR rates that normalized correctly and flowed through the checkout path; no production credentials were used and no destructive operation was performed. Post-MVP #5 re-verified the sandbox with a parcel carrying actual product dimensions/weight (1200 g, 35×22×12 cm, quantity 2 → 2 parcels) — the live request body carried the real measurements and the sandbox returned a real ZAR rate.

## Payment Architecture (Sprint 3, Part 3)

- **Provider abstraction:** `features/payment/types.ts` defines a `PaymentProvider` interface (`isConfigured`, `createSession`, `handleWebhook`). Checkout business logic never imports a specific gateway; it goes through `features/payment/provider-registry.ts` which only registers gateways whose server-side credentials are present. Additional gateways (Yoco, Stitch) can drop in behind the same interface.
- **Providers:**
  - **Stripe** (`features/payment/stripe.ts`) — hosted Checkout Sessions via direct Stripe API calls (no `stripe` npm dependency). Webhook signature verified with HMAC-SHA256 + `STRIPE_WEBHOOK_SECRET` and `timingSafeEqual`. Implemented and unit-tested against real signature math; NOT marked production-ready because it has not been exercised against the live Stripe API with real credentials.
  - **PayFast** (`features/payment/payfast.ts`) — hosted PayFast form (sandbox/production endpoint selected by `PAYFAST_TEST_MODE`). ITN callback verified with MD5 over sorted POST fields + `PAYFAST_PASSPHRASE`. Implemented and unit-tested against real signature math; NOT marked production-ready because it has not been exercised against the live PayFast sandbox with real credentials.
  - **Yoco** (`features/payment/yoco.ts`) — hosted Checkout API (`POST https://payments.yoco.com/api/checkouts`, Bearer auth, JSON body with `amount`/`currency`/`successUrl`/`cancelUrl`/`metadata`, returns `redirectUrl` + `id`). Webhook verified with the Standard Webhooks scheme (`webhook-id`/`webhook-timestamp`/`webhook-signature` headers, HMAC-SHA256 over `id.timestamp.body` with the base64-decoded `whsec_` `YOCO_WEBHOOK_SECRET`). Implemented per the official public API contract and unit-tested against real signature math (mocked `fetch` for `createSession`); NOT marked production-ready because it has not been exercised against the live Yoco API with real credentials. Registered and selectable behind the abstraction when both Yoco env vars are set; checkout routing still defaults to PayFast (SA) / Stripe (international).
  - **Stitch** (`features/payment/stitch.ts`) — hosted payment-initiation via the official `clientPaymentInitiationRequestCreate` GraphQL mutation (`POST https://api.stitch.money/graphql`, Bearer client token obtained via the OAuth 2.0 client-credentials flow with the `client_paymentrequest` scope, `Idempotency-Key` header = intent id). The mutation input sends `amount.quantity` in MAJOR units (Rand) — NOT cents — with `externalReference` set to the CheckoutIntent id (the webhook correlation key), `payerReference`/`beneficiaryReference` derived from the order number and clamped to the documented limits (≤12 / ≤20), `payerInformation.payerId` = customer email (recommended for fraud checks), and `expireAt` (ISO 8601, now + 30 min). The response `paymentInitiationRequest { id url }` provides the provider reference and the hosted url, to which `redirect_uri` (success) and `failure_redirect_uri` (cancel) are appended. Webhook verified with Svix/Standard Webhooks (`svix-*` headers, shared `standard-webhooks.ts` verifier, `STITCH_WEBHOOK_SECRET`); the webhook `amount.quantity` is converted from major units back to cents so the authoritative-amount guard matches the server-computed intent. Implemented per the official public API contract and unit-tested against real signature math (mocked `fetch` for `createSession`); NOT marked production-ready because it has not been exercised against the live Stitch sandbox with real credentials. Registered and selectable behind the abstraction when `STITCH_CLIENT_ID` + `STITCH_CLIENT_SECRET` + `STITCH_WEBHOOK_SECRET` are all set; checkout routing still defaults to PayFast (SA) / Stripe (international).
  - **Test** (`features/payment/test.ts`) — mock gateway for local dev and automated tests. Hosted "payment page" is `/checkout/test-pay`; the completion callback is HMAC-signed with `TEST_PAYMENT_SECRET` and still passes server-side verification. Only registered outside production (`NODE_ENV !== "production"`).
- **Standard Webhooks verifier:** `features/payment/standard-webhooks.ts` is a dependency-free (Node `crypto` only) implementation of the Standard Webhooks specification, shared by Yoco and Stitch/Svix. It enforces: required headers (fail-closed), `whsec_` secret prefix + base64 decode, HMAC-SHA256 over `id.timestamp.body` with the RAW request body, constant-time signature comparison, space-separated `v1,<sig>` list parsing (accepts the first matching `v1` entry, ignores `v0`/`v2` for forward-compatible key rotation), replay protection (default 180s tolerance, hard max 3600s), and a 1 MiB body-size guard. Pure (no `server-only`) so it imports directly under Node's native test runner.
- **Provider selection:** `selectProviderForCountry` routes South Africa → PayFast (guidebook default) and international → Stripe. When the selected real gateway is not configured (local dev without credentials), the flow falls back to the Test provider. Yoco and Stitch are registered but not selected by the default country routing; they are selectable when explicitly requested and configured.
- **Intent-based flow (no order until paid):**
  1. `startCheckoutPaymentAction` (`features/payment/actions.ts`) validates the form, creates a PENDING `CheckoutIntent` with an authoritative server-computed amount (re-read from PostgreSQL), selects the provider server-side, creates the hosted-payment session, and returns the redirect URL. No `Order` is created and no inventory is touched at this stage.
  2. The shopper is redirected to the gateway's hosted payment UI (raw card data never touches ShopNova).
  3. The gateway posts a signed webhook/ITN to `/api/webhooks/{provider}`.
  4. `features/payment/webhook-handler.ts` → provider `handleWebhook` verifies the signature server-side and throws on failure (the browser is never trusted).
  5. `lib/db/payments.ts` `completePaidIntent` runs the verified notification atomically: claims the intent with a `status: PENDING` + `completedPayloadKey: null` guarded `updateMany` (idempotency), re-reads authoritative products + inventory, validates quantities, recalculates prices, finds-or-creates the Customer, creates the `Order` as `CONFIRMED` (paid), creates `OrderItem` price snapshots, decrements inventory with a quantity guard, and records a `SUCCEEDED` `Payment`. The cart is cleared only after the transaction commits.
- **Security guarantees:**
  - An order is only created (and only marked paid) after a server-verified provider notification. Browser-supplied success is never trusted.
  - Payment amounts are derived from authoritative server/DB values, never client-supplied totals. The gateway's verified charge must exactly match the server-computed intent amount (cents) **and** currency, or the notification is rejected as `amount-mismatch`.
  - Webhook processing is provider-specific: a verified notification from gateway X cannot complete a `CheckoutIntent` created for gateway Y. Enforced in `completePaidIntent` via the pure `isProviderMatch` helper (`features/payment/payment-logic.ts`), in addition to each route being provider-scoped (`/api/webhooks/{provider}`) and each adapter verifying its own signature — defence in depth. A mismatch is rejected as `provider-mismatch` (HTTP 400).
  - The mock Test gateway completion path (`completeTestPaymentAction`, `/checkout/test-pay`) is refused unless the server is outside production, the intent's provider is `test`, and the intent belongs to the calling shopper.
  - Duplicate webhook deliveries are idempotent: the unique `completedPayloadKey` + guarded status transition prevent double order creation or double inventory decrement.
  - Raw card numbers, CVV, etc. never reach ShopNova servers (hosted Stripe Checkout / PayFast form / Yoco Checkout / Stitch hosted UI / mock page).
- **Webhook routes:** `/api/webhooks/stripe`, `/api/webhooks/payfast`, `/api/webhooks/yoco`, `/api/webhooks/stitch`, `/api/webhooks/test` — thin route handlers delegating to the shared `handleProviderWebhook`. HTTP status codes: 200 (processed/duplicate/failed/ignored), 400 (signature failure / provider not configured / amount mismatch / provider mismatch), 404 (intent not found), 500 (unexpected error).
- **Shipping seam:** `features/shipping/shipping-provider.ts` introduces a `ShippingProvider` interface (`quote`). The default `MvpShippingProvider` keeps the deterministic free-above-$50 / flat-$5 rule from checkout-logic. Live courier integrations (Bob Go, Aramex, PUDO, Courier Guy) can later implement the same interface and be registered without touching checkout business logic or the UI.
- **Tests:** 11 payment-logic tests (`features/payment/payment-logic.test.ts`) + 15 webhook verification tests (`features/payment/payment-webhook.test.ts`) + 16 Standard Webhooks verifier tests (`features/payment/standard-webhooks.test.ts`) + 36 Yoco + Stitch provider behavior tests (`features/payment/yoco-stitch.test.ts`) using the REAL provider adapter code with mock credentials and real signature math. The Stitch tests cover the `createSession` GraphQL request/response contract (endpoint, Bearer auth, `Idempotency-Key`, `amount.quantity` in major units, `externalReference` = intent id, reference clamping, `redirect_uri`/`failure_redirect_uri` appending, GraphQL `errors[]`, missing id/url), the pure helpers (`centsToStitchMajorUnits`/`majorUnitsToCents` round-trip, `stitchReference`, `buildStitchRedirectUrl`), and the Svix webhook event parsing. The test runner shims the `server-only` marker package via `scripts/test-register.mjs` + `scripts/test-loader.mjs` so provider modules can be imported outside a React server context; the loader also retries extensionless relative `.ts` imports (which production bundlers resolve but Node's `--experimental-strip-types` does not auto-append for value imports).

## Customer Accounts & Order History (Sprint 4)

- **Clerk ↔ Customer link:** A nullable, unique `Customer.clerkUserId` column (additive schema change) associates an authenticated Clerk user with their existing Customer row. The link is set during checkout inside `completePaidIntent` when the shopper is signed in (`shopperId` starts with `user:<clerkUserId>`). Guest checkouts leave `clerkUserId` null. Clerk remains the authentication source of truth; no second auth system is introduced.
- **Customer resolution:** `lib/db/customers.ts` `getCustomerForClerkUser(clerkUserId)` resolves the authenticated Clerk user to their Customer row (within the default store). Returns null for a brand-new account that has never completed a signed-in checkout.
- **Authorized order queries:** `lib/db/orders.ts` adds `getOrdersForCustomer(customerId)` and `getOrderForCustomer(customerId, orderNumber)`. Both scope every query to the authenticated customer's id — this is the authorization boundary. A foreign order number returns null (identical to a missing one), so a customer can neither view nor confirm another customer's order by manipulating the URL.
- **Pure auth helpers:** `features/account/account-logic.ts` provides `clerkUserIdFromShopperId`, `isOrderOwnedByCustomer`, `assertOrderOwnedByCustomer`, and `buildDisplayName` — side-effect-free functions unit-tested with Node's native test runner.
- **Routes:** `/account` (overview with Clerk name/email + order count), `/account/orders` (order history table with empty-state), `/account/orders/[orderNumber]` (order detail: items, line totals, subtotal/VAT/shipping/total, shipping/contact info, payment summary). All three redirect unauthenticated users to `/sign-in?redirect_url=...` via in-page `redirect()`.
- **Auth strategy:** In-page `redirect()` is used instead of middleware `auth.protect()` because Clerk v7 deprecates `createRouteMatcher` and `auth.protect()` returns 404 (instead of redirecting) under Next.js 16. The in-page check is the recommended resource-based approach per Clerk's migration guide.
- **Navigation:** `components/storefront/account-button.tsx` shows "Sign in" for anonymous shoppers and an Account link + Clerk `UserButton` for signed-in shoppers. Added to the marketing header alongside the cart button.
- **Existing data:** The schema change is additive. Existing customers/orders are preserved. Existing guest-checkout customers have `clerkUserId = null` and their orders are not accessible through the account area (by design — they were placed as a guest).
- **Tests:** 15 account-logic tests (`features/account/account-logic.test.ts`) covering Clerk/customer association, order ownership (own / foreign / guest / missing), `assertOrderOwnedByCustomer` throw behavior, and display-name fallbacks. Total test suite: 71 tests.

## Admin Dashboard & Store Management (Sprint 5)

- **Authorization approach:** An admin is a Clerk user whose `privateMetadata.role === "admin"`. `privateMetadata` is only readable server-side via the Clerk Backend API (`currentUser()`), so a customer can never learn or forge admin status in the browser, and users cannot set their own privateMetadata. No second auth system is introduced — Clerk remains the source of truth. Grant/revoke the role with `npm run set-admin -- <clerkUserId> [--remove]` (`scripts/set-admin.ts`, uses `CLERK_SECRET_KEY`) or via the Clerk Dashboard.
- **Server-side enforcement:** `lib/auth/admin.ts` provides `requireAdmin()` (throws `UnauthenticatedError`/`AdminRequiredError`, used in every admin server action), `requireAdminOrRedirect()` (redirects to sign-in / `/dashboard/unauthorized`, used at the top of every admin page), and `getAdminContext()` (non-throwing, used for the storefront header link). Pure helpers + errors live in `features/admin/admin-logic.ts` (`isAdminRole`, `assertAdminRole`, `roleFromMetadata`, order-status rules) so they can be unit-tested without Clerk credentials.
- **Middleware:** A lightweight authentication gate redirects unauthenticated `/dashboard(.*)` requests to `/sign-in?redirect_url=/dashboard`. Role *authorization* is NOT done in middleware because `privateMetadata` is not present in the JWT — it happens in-page and in server actions. ## Final MVP Audit (Sprint 7)

A full audit of the implementation against the MVP requirements in `GUIDEBOOK.md`, covering the customer journey, admin journey, security boundaries, data integrity, payment safety, responsive UX, and the test suite. Findings and fixes:

- **Forgeable paid order via the mock Test gateway (security, high).** `completeTestPaymentAction` built a "verified" notification from the intent's own amount with no environment gate, no provider check, and no ownership check — and `/checkout/test-pay` is compiled into every build. A client could therefore start a real Stripe/PayFast checkout and complete it for free, or complete/decline another shopper's intent. Fixed: both the action and the page now require `NODE_ENV !== "production"`, `intent.provider === "test"`, and `intent.shopperId === ` the current shopper (pure `isTestPaymentAllowed` in `features/payment/payment-logic.ts`). Refusals are non-informative (`not-found` / `notFound()`). Identity is resolved with a read-only `getExistingShopperId()` (null for a shopper with no cart cookie) rather than `getShopperId()`, which mints the anonymous cookie — a Server Component may not set cookies, so the minting variant made a first-ever visit crash instead of being denied.
- **Authoritative-amount guard ignored currency (payment safety).** `completePaidIntent` compared minor units only, so a verified notification in another currency with the same minor amount passed. Fixed with a case-insensitive `currencyMatches` check (intents store `ZAR`, providers report `zar`); a mismatch is rejected as `amount-mismatch` before any order/payment is created.
- **Archived products were still orderable (data integrity).** `getCheckoutSummaryAction` silently skipped archived cart lines while `startCheckoutPaymentAction` still passed them through, and neither product load in `lib/db/payments.ts` filtered `archived: false` — so an item archived after being added to the cart was charged for at a total higher than the summary displayed. Fixed: both authoritative product loads exclude archived products, checkout returns an actionable error, and the cart marks such lines unavailable and excludes them from totals and the header count.
- **Admin helpers documented as store-scoped but not scoped (defence in depth).** `updateProduct`/`deleteProduct`/`restoreProduct`, `updateCategory`/`deleteCategory`, and `listInventory` resolved the default store id and then ignored it; product create/update accepted any `categoryId`. Fixed by verifying row (and referenced category) ownership before mutating, matching the pattern already used by `updateInventory`. Single-store MVP, so this was not a live exposure.
- **Storefront category counts included archived products (correctness).** `/categories` and the home page advertised counts that included soft-deleted items. Fixed; the admin categories page explicitly requests total counts so admin numbers stay accurate.
- **UX (MVP-level).** The storefront nav was hidden below `md` with no mobile alternative, making Products/Categories/About/Pricing/Contact unreachable on a phone — a compact mobile menu (`components/storefront/mobile-nav.tsx`) was added; it closes after navigation, its panel is pinned inside the viewport, and the header's search control collapses to an icon below `sm` so there is no horizontal overflow at 390px. The admin topbar's non-functional "Search..." box was removed (admin search is not in MVP scope).
- **Tests:** 8 new pure-logic tests — the mock-payment gate (production, non-test provider, foreign shopper, missing shopper identity, intended local case), the currency guard (case-insensitive match, mismatch), and archived cart lines excluded from subtotal/item count. Total test suite: **119 tests**.
- **Runtime verification:** the storefront journey was exercised in a browser against seeded PostgreSQL — browse/search, cart quantity and removal, checkout arithmetic (VAT/shipping), the mock-gateway pay and decline paths (order, order items, price snapshots, `SUCCEEDED` payment, inventory decrement and the no-order decline path all confirmed in the database), the archived-product guard, the ownership gate, and the 390px layout. That run found and we then fixed the two regressions noted above (cookie-less test-pay crash, mobile header overflow).

## Stitch Payment-Gateway Completion (Post-MVP #3)

The previous milestone implemented Yoco and the Stitch/Svix webhook foundation, but left `StitchProvider.createSession` intentionally unimplemented because the exact `clientPaymentInitiationRequestCreate` GraphQL mutation contract was not available. This milestone completes and production-hardens the Stitch integration now that the official documentation (docs.stitch.money) publishes the full contract.

- **Official contract verified:** `clientPaymentInitiationRequestCreate(input: ClientPaymentInitiationRequestCreateInput!): ClientPaymentInitiationRequestCreatePayload` at `POST https://api.stitch.money/graphql`, authenticated with a Bearer client token (OAuth 2.0 client-credentials, `client_paymentrequest` scope) and an optional `Idempotency-Key` header. The input requires `amount: MoneyInput!` (`{ quantity: Decimal!, currency: CurrencyCode! }`), `payerReference: String!` (≤12), and `beneficiaryReference: String!` (≤20); optional fields include `externalReference` (≤4096), `payerInformation.payerId`, and `expireAt` (ISO 8601). The payload returns `paymentInitiationRequest: PaymentInitiationRequest!` with `id: ID!` and `url: URL!`. The hosted `url` takes an allowlisted `redirect_uri` (and optional `failure_redirect_uri`) query parameter.
- **Critical correctness fix (major units):** the official docs confirm `MoneyInput.amount.quantity` is in MAJOR units (Rand), NOT cents (Money scalar example `{"quantity":"100.23"}`; OTA API "amount in major units (e.g. 350.5 for R350.50)"). The previous webhook handler treated `quantity` as cents — a latent bug that would have made every real Stitch webhook fail the authoritative-amount guard (fail-closed/safe, but Stitch could never complete a payment). Replaced `parseStitchAmount` with `majorUnitsToCents` (`Math.round(Number(quantity) * 100)`) and added `centsToStitchMajorUnits` (pure integer math, 2-dp string) so the create→webhook round-trip is consistent with the server-computed intent amount.
- **`createSession` implementation:** obtains a client token via the existing `getStitchClientToken` helper, POSTs the GraphQL mutation with Bearer auth + `Idempotency-Key` (intent id), sets `externalReference` = intent id (the webhook correlation key), `payerReference`/`beneficiaryReference` derived from the order number (sanitized + clamped to the documented limits), `payerInformation.payerId` = customer email (recommended for fraud checks), and `expireAt` = now + 30 min. It parses `paymentInitiationRequest { id url }`, appends `redirect_uri` (success) + `failure_redirect_uri` (cancel) to the hosted url, and returns `{ provider, redirectUrl, providerReference: id }`. Non-OK HTTP, GraphQL `errors[]` (with extension code), a missing id, and a missing url each throw a clear error.
- **Selectability gate:** `StitchProvider.isConfigured()` returns true only when the creation flow is implemented AND all three server-side credentials are present (`STITCH_CLIENT_ID` + `STITCH_CLIENT_SECRET` + `STITCH_WEBHOOK_SECRET`). The provider can never be selected by checkout until the complete flow + credentials are in place. Checkout routing still defaults to PayFast (SA) / Stripe (international); Stitch is selectable when explicitly requested and configured.
- **Security unchanged and re-verified:** all credentials stay server-side (`import "server-only"`); the browser redirect `status` is never trusted for payment state (signed Svix webhook only); provider matching (`isProviderMatch`), Svix signature verification (shared `standard-webhooks.ts` verifier), intent ownership, authoritative amount + currency validation (`amountMatches`/`currencyMatches` in `completePaidIntent`), replay protection (Svix timestamp tolerance), idempotency (`completedPayloadKey` + guarded PENDING→COMPLETED transition), and webhook-driven payment-state transitions all remain intact. Existing security tests were not weakened.
- **Pure helpers exported:** `centsToStitchMajorUnits`, `majorUnitsToCents`, `stitchReference`, `buildStitchRedirectUrl` — unit-tested directly.
- **Tests:** 14 new/updated Stitch tests in `features/payment/yoco-stitch.test.ts` (Yoco + Stitch file now 36 tests). Existing Stitch webhook tests updated to the real major-unit contract (`quantity: "115.00"` → 11500 cents). Total suite: 255 tests.
- **No schema change** was required or made.
- **Status:** implemented per the official public API contract and unit-tested against real signature math (mocked `fetch` for `createSession`). NOT exercised against the live Stitch sandbox (no `STITCH_*` credentials in this environment), so it is not marked production-verified. Live-API verification remains pending real credentials.

## Catalog Federation (Demo Step 3, GUIDEBOOK §8)

Links an external store (Shopify/Amazon/Takealot/AliExpress/WooCommerce/CSV) so its products can be imported, marked up, and resold with auto-sync.

- **Schema (additive):** `FederationLink` (source, name, config JSON, lastSyncedAt, errorMessage), `FederationSyncRun` (RUNNING/SUCCESS/FAILED, created/updated/removed counts, errors), and `Product.federationLinkId` + `Product.externalId` (nullable; `onDelete: SetNull` so historical orders stay intact when a link is removed). Migrations: `prisma/migrations/*`.
- **Data layer (`lib/db/federation.ts`):** `applyMarkup` (percentage `base * (1 + value/100)` or fixed `base + value`, rounded to 2dp), link CRUD (`listFederationLinks`, `getFederationLinkById`, `createFederationLink`, `deleteFederationLink`), `listFederationSyncRuns`, and the sync runner `runFederationSync`. The runner creates a `RUNNING` sync run, pages through upstream products, upserts each as a federated `Product` (matched by `externalId`), updates the run to `SUCCESS` with counts, and on failure marks it `FAILED` and rethrows.
- **Upsert strategy:** same-link re-sync updates existing products (re-applying markup so upstream price changes flow through); an orphaned product left by a removed source (federationLinkId = null, same externalId) is re-linked instead of duplicated; genuinely new products get a store-unique slug. Inventory and the primary image are kept in sync with the upstream on re-sync.
- **Link deletion:** runs in a single transaction. Products that have never been ordered are hard-deleted (images/inventory cascade); products on historical `OrderItem`s are archived + unlinked (preserving order history, mirroring the soft-delete policy). `FederationSyncRun` rows cascade-delete with the link.
- **Mock sources (`lib/federation/mock-sources.ts`):** DEMO-only stand-in for the real per-source connectors. Returns a fixed, realistic, source-specific catalog (Shopify, Amazon, Takealot, AliExpress, WooCommerce, CSV) so the federation demo runs with no external credentials, network, or chance of failure. The `UpstreamProduct` shape mirrors what a real source client would return, so swapping this file for real per-source clients later requires no changes to the runner.
- **Dashboard (`/dashboard/federation`):** admin-gated. Lists linked sources (source, name, product count, last sync, status pill) with Sync + Remove actions, and a recent sync runs table. The `FederationForm` creates a new link (name, source, target category, markup type/value, sync interval) validated with `federationLinkSchema` (`lib/validations/federation.ts`).
- **Server actions (`app/(dashboard)/dashboard/federation/actions.ts`):** `createFederationLinkAction`, `runFederationSyncAction`, `deleteFederationLinkAction` — all authorize via `requireAdmin()` before any DB write and `revalidatePath` the federation page, products page, and storefront so new/removed products appear immediately.
- **Security:** every action/page authorizes via `requireAdmin()`/`requireAdminOrRedirect()`; the target category is verified to belong to the default store before a link is created. Courier/source credentials are server-only.

- **Security:** the action authorizes via `requireAdmin()` before any DB read. The cart id is resolved server-side from the store's real customers/products; no client input is trusted for the email contents.

## Demo Order Seeding (`prisma/seed-orders.ts`)

The main seed (`prisma/seed.ts`) creates the store, categories, products, and inventory — but NO customers and NO orders. `seed-orders` fills that gap so the dashboard's "Recent orders" table, the AI insights growth %, and the Active Carts & Recovery feed all have realistic data.

- **Creates:** 6 customers (also used by the abandonment feed) and ~40 orders spread across THIS month and LAST month, weighted so Electronics leads growth (~+42–50%), followed by Fashion — exactly the story the AI insights demo tells.
- **Idempotent:** safe to run multiple times. It does NOT delete existing orders/customers; it only creates what's missing (upserts customers by `[storeId, email]`, skips orders whose `orderNumber` already exists). Re-running after a month boundary simply adds more orders to the new "this month".
- **Requires:** `npm run db:seed` must be run first (it needs the store, categories, and products).
- **Run:** `npm run db:seed-orders`.
